# TALARIA production readiness master plan

This plan expands every baseline requirement in [the implementation tracker](IMPLEMENTATION_TRACKER.md) into a traceable work item. The tracker remains the baseline for requirement wording and current implementation evidence. Status is inherited from the tracker and is not upgraded by this plan.

## Architecture map

| Boundary | Responsibility and consumers | Persistence / security boundary | Current verification |
|---|---|---|---|
| API and dashboard | `talaria/api.py` exposes FastAPI routes; `talaria/dashboard/` is the analyst UI and calls the API. | API role and tenant checks are authoritative; dashboard state is not authorization. | Local API tests; public deployment/ingress is not validated. |
| Identity and approvals | `talaria/auth/` owns password, session, role and approval flows. | `users`, `organizations`, `organization_memberships`, `refresh_sessions`, `approval_records`; tenant/action checks occur server-side. | Auth and role matrix tests. |
| Storage and migration | `talaria/database.py`, `migrations.py`, `postgres_schema.py` support SQLite and PostgreSQL. | Explicit CLI migrations, checksums, tenant constraints, backups; startup paths should be read-only. | SQLite local; PostgreSQL integration tests require configured disposable service. |
| Scanning and findings | `talaria/scanning/`, `repositories/`, `findings/` collect deterministic results. | Repository paths are constrained; results, occurrences and scans are database-backed. | Local scanner/API tests. |
| Integrations | `talaria/integrations/` handles GitHub webhooks/App operations and LLM calls. | Secrets are file-backed; external writes are approval-gated; source sharing is opt-in. | Mocked provider tests only; user requested local/mock checks. |
| Audit and security | `talaria/audit/`, `talaria/security/`, database audit writers. | Schema v14 chains audit rows; SQLite blocks ordinary updates/deletes and all runtime writers use the centralized append method. A full-chain rewrite by a database owner is not independently detectable. | Local tamper and readiness tests pass; immutable external checkpoints and live PostgreSQL verification remain open. |
| Deployment and CI | `Dockerfile`, Compose, Kubernetes YAML, `.github/workflows/ci.yml`. | Non-root/restricted containers, secret mounts, internal DB network, CI gates. | YAML and unit checks; Docker/Kubernetes runtime unavailable locally. |

## Cross-cutting security and reliability review

* Dependencies: database migrations precede persisted workflows; identity/tenant authorization precedes integrations; deterministic scanning must remain independent from AI; approval precedes provider writes; deployment and observability precede production use.
* Security implications: every route and database read/write must carry verified principal and organization context; secrets, source, prompts, tokens, and private repository data must not enter logs; LLM output is untrusted; provider writes must be exact-operation approved and idempotent.
* Failure behavior: migrations fail closed; scans/investigations have bounded input/time/resources; provider timeouts and retries do not duplicate writes; restore targets are new/empty; readiness reports unavailable dependencies without mutating storage.
* Independent verification: the implementation author’s tests are not an independent security review. A reviewer must inspect authz/tenant queries, migration safety, patch and GitHub write boundaries, secret handling, and the deployed ingress.
